relay — authentication and authorization, end to end

How a caller gets a credential, what that credential reaches, and what a refusal looks like.

This page is for the two people who have to act on it: an engineer wiring a new consumer to relay's HTTP control plane, and an operator who needs to know what a credential can reach and how to get one. It assumes HTTP and public-key crypto and nothing about relay.

It is the flow. docs/tokens.md is the inventory — the canonical table of every credential in the ecosystem, and where each lives at rest. docs/audit-log.md is the record format. The reasoning lives in ADR-014, ADR-015 and ADR-016; those argue, this explains.

Every command and every response on this page was executed. Nothing here is composed by hand. The transcripts come from a relay built with ./build.sh --test and started against a throwaway config directory (relay --config-dir /tmp/relaydoc) with RELAY_API_LISTEN=127.0.0.1:8790, so nothing here touched a real install. The relay in each transcript is /Applications/Relay.app/Contents/MacOS/relay --config-dir /tmp/relaydoc, shortened for reading. Secrets are truncated in place and marked with … — the shape is real, the value is cut. Credential ids and passkey ids are identifiers, not secrets, and are shown whole, because the audit output refers to them.

1. Fifteen minutes, from nothing to a working credential

The control plane is an HTTP API. It always has a 0600 Unix socket. It has a loopback TCP listener only if you asked for one:

RELAY_API_LISTEN=127.0.0.1:8790 /Applications/Relay.app/Contents/MacOS/relay
RELAY_API_LISTEN=127.0.0.1:8790 open -a Relay      # also works — open passes the environment on

Relay must not already be running when you do this, or open merely activates the existing process. Confirm the bind before going further:

$ lsof -nP -iTCP:8790 -sTCP:LISTEN
COMMAND   PID  USER   FD   TYPE             DEVICE SIZE/OFF NODE NAME
relay   18066 admin    8u  IPv4 0xc97e17983d2959df      0t0  TCP 127.0.0.1:8790 (LISTEN)

Mint a credential on the host. The token is printed once:

$ relay credential mint --name doc-readonly --class read
minted credential "doc-readonly"
  id:      0c49e4b1-c5fb-420b-a473-6685b9403769
  classes: read
  created: 2026-08-28T23:09:46Z
  expires: never
  token:   0e4fd44e6e6bc693…
  this token is shown ONCE and is not recoverable — only its SHA-256 is stored
  present it as: Authorization: Bearer <token>

Use it:

$ curl -sS -i -H "Authorization: Bearer 0e4fd44e6e6bc693…" http://127.0.0.1:8790/api/projects
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 3

[]

Ask it to do something it was not granted, and see the shape of a refusal:

$ curl -sS -i -H "Authorization: Bearer 0e4fd44e6e6bc693…" \
       -H 'Content-Type: application/json' -d '{"name":"x"}' \
       http://127.0.0.1:8790/api/projects
HTTP/1.1 403 Forbidden
Content-Type: text/plain; charset=utf-8

Forbidden

Then check the ground truth. The agent's — or the caller's — own account of what it could reach is not evidence; relay audit is:

$ relay audit --kind control
TIME      OUTCOME  PROJECT  MCP  TOOL  MS  CALLER                                DETAIL
16:09:54  ok       -        -    -     0   0c49e4b1-c5fb-420b-a473-6685b9403769  GET /api/projects  class=read  transport=tcp
16:09:54  denied   -        -    -     0   0c49e4b1-c5fb-420b-a473-6685b9403769  POST /api/projects  class=configure  transport=tcp  class not granted

Everything below is that loop, with the reasons.

2. The credential model

Relay has several credentials, and only some of them are about the HTTP control plane this page describes. The distinction matters when you are debugging: presenting the wrong one gets you a 401 that says nothing about which door you knocked on.

CredentialReachesHeld byIssued byAt rest
Project token
RELAY_PROJECT_TOKEN		 The bridge, not this API. Scopes MCP tool calls to one project. Project shells, LLM CLIs, the relay mcp child Relay, per project Plaintext + SHA-256 inline in the project in settings.json
Service token
RELAY_SERVICE_TOKEN		 The bridge, unfiltered — broker and admin ops. A spawned enhanced service Relay, per spawn In memory only; never persisted, never given to a child shell
Frontend token
RELAY_FRONTEND_TOKEN		 This API, as a credential — see below. Eve, relayScheduler Relay, fresh per process start SHA-256, as the legacy-frontend-token record
Control-plane credential
api_credentials		 This API, on the classes it names. Whatever you hand it to relay credential mint SHA-256 in settings.json
Login credential This API, read+configure, for 12 hours. One browser tab, in memory A passkey assertion at /relay/login SHA-256, as an ordinary api_credentials record
Enhanced-service internal bearer One service's own internal socket. Relay's dispatcher The service, declared at RegisterManifest In relay's in-memory manifest registry
Login bootstrap code Nothing. It authorises registering a passkey. The operator's eyes, for two minutes relay login enrol SHA-256 + expiry in settings.json

Two more exist and are out of scope here: the admin_secret that gates a handful of bridge ops, and per-MCP OAuth tokens that authenticate relay to upstream servers. docs/tokens.md has both.

The control-plane credential

This is the one thing the HTTP API authenticates. It carries a name, a SHA-256 of a token relay printed once, an explicit set of classes, a creation time, and optionally an expiry. Here is a real record set, straight out of a sandbox settings.json with the hashes cut:

{
  "api_credentials": [
    {
      "id": "245e087e-7c8f-47e1-9bf8-adf83cc79c45",
      "name": "legacy-frontend-token",
      "hash": "04ae7a030e238742…",
      "classes": ["read", "configure", "proxy"],
      "created": "2026-08-28T23:09:33Z"
    },
    {
      "id": "9fe92b8e-622b-4a73-8b94-36a1da1f7f80",
      "name": "doc-executor",
      "hash": "13bb6a58e17cc25c…",
      "classes": ["read", "execute"],
      "created": "2026-08-28T23:09:46Z"
    },
    {
      "id": "1366dbe3-b5ee-482c-993a-9e02d6822018",
      "name": "doc-shortlived",
      "hash": "4f3f794a11838299…",
      "classes": ["read"],
      "created": "2026-08-28T23:10:48Z",
      "expires": "2026-08-28T23:11:18Z"
    }
  ]
}

Rules worth knowing before you mint one:

  • An absent class set grants nothing. Never "everything", never "read". A credential written by a tool that predates the class model is inert. The CLI refuses to mint one, because a credential that silently reaches nothing is worse to debug than an error at the point of entry: 
    $ relay credential mint --name doc-nothing
error: at least one class is required (read,configure,grant,execute,proxy); a credential with no class can reach nothing

$ relay credential mint --name doc-typo --class reed
error: unknown class "reed"; valid classes are read,configure,grant,execute,proxy
  • Classes do not nest. grant does not imply read. A grant-only credential cannot list projects: 
    $ curl ... -H "Authorization: Bearer fe42793646211c38…" http://127.0.0.1:8790/api/projects
403
  • No --ttl means no expiry, and absent is the compatible value. A record written before the field existed round-trips unchanged. A negative lifetime is an operator mistake, not a way to mint something already dead: 
    $ relay credential mint --name doc-negative --class read --ttl -1h
error: a negative lifetime (-1h0m0s) is not a credential; omit --ttl for one that never expires
  • Expired records are reaped lazily, inside the same settings write as the next mint or the next login — never on a timer. Reaping is housekeeping, not enforcement: a credential stops authenticating the moment it expires, swept or not. list hides expired records; --include-expired shows what the next mint will sweep: 
    $ relay credential list --include-expired
ID                                    NAME                   CLASSES               CREATED               EXPIRES
245e087e-7c8f-47e1-9bf8-adf83cc79c45  legacy-frontend-token  read,configure,proxy  2026-08-28T23:09:33Z  never
9fe92b8e-622b-4a73-8b94-36a1da1f7f80  doc-executor           read,execute          2026-08-28T23:09:46Z  never
0c49e4b1-c5fb-420b-a473-6685b9403769  doc-readonly           read                  2026-08-28T23:09:46Z  never
1366dbe3-b5ee-482c-993a-9e02d6822018  doc-shortlived         read                  2026-08-28T23:10:48Z  2026-08-28T23:11:18Z (expired)
    Neither the plaintext nor the hash is ever printed by list. The hash verifies a live secret, so a listing that showed it would put an offline-guessable value into scrollback.
  • Revoking is immediate, because authorization reads the settings file through a stat-and-reload rather than a cached view. There is no restart and no poll interval — the same guarantee relay enrol create gets. 
    $ relay credential revoke --id 6d6c25d7-fd98-4142-852b-705dc296bb32
revoked credential "6d6c25d7-fd98-4142-852b-705dc296bb32"
  name:    doc-reader
  classes: read,configure
  its token stops authenticating on the next request; nothing else was touched

$ curl -o /dev/null -w '%{http_code}\n' -H "Authorization: Bearer 56f2978b4866a7fb…" http://127.0.0.1:8790/api/projects
401

The frontend token, and the credential it migrates to

Consumers relay spawns itself — Eve, relayScheduler — receive RELAY_FRONTEND_TOKEN and RELAY_FRONTEND_SOCKET in their environment. That token is not a second authentication path. On every start relay records it as one control-plane credential named legacy-frontend-token, holding exactly read + configure + proxy:

$ relay credential list                     # on a config directory that had never been used
ID                                    NAME                   CLASSES               CREATED               EXPIRES
245e087e-7c8f-47e1-9bf8-adf83cc79c45  legacy-frontend-token  read,configure,proxy  2026-08-28T23:09:33Z  never

Three consequences, all of which will bite someone eventually.

  • The plaintext changes on every relay start — relay mints a fresh 32-byte token per process. The migration finds the record by name and overwrites its hash in place, so restarting does not accumulate a new legacy credential each time.
  • The name is reserved. You cannot mint or revoke it by hand, because the next start would silently clobber whatever you put there: 
    $ relay credential mint --name legacy-frontend-token --class read
error: "legacy-frontend-token" is reserved for the RELAY_FRONTEND_TOKEN migration, which rewrites its hash on every relay start; it cannot be minted or revoked by hand
  • Its class set is a narrowing, and it is overwritten rather than merged. The legacy token never holds grant or execute. If your consumer rotates project tokens, creates enrolments, registers an MCP or writes a service's command, it needs a credential of its own — relay credential mint --name my-rotator --class grant. Editing a wider class set onto the record by hand does not survive the next start.

The enhanced-service internal bearer

An enhanced service (relayLLM, relayScheduler) picks its own internal socket and its own token, and declares both to relay through RegisterManifest. When relay proxies a front-door request onward, it strips the caller's inbound Authorization header and injects the service-declared one. The two trust boundaries never touch: the caller's credential authorises reaching the proxied surface at all, and the service's own bearer is what the service sees. This is why the class on that mount is proxy and not something more specific — see the class model.

The login credential

An interactive login mints an ordinary api_credentials record. There is still exactly one thing the API authenticates and one place an operator revokes. What is special is only its shape:

$ relay credential list
ID                                    NAME                                      CLASSES         CREATED               EXPIRES
69a9acee-a6a8-4be9-aa3a-a11c6135ef86  login 3FPKcJeU-R7J… 2026-08-28T23:12:59Z  read,configure  2026-08-28T23:12:59Z  2026-08-29T11:12:59Z
  • read + configure, and nothing else. Never grant — a view that can rotate a project token is a view whose compromise issues credentials. Never execute, which is unroutable on TCP anyway; stating it on the credential means the refusal survives someone later serving the view over the socket. Never proxy, which is what makes configure mean what it says: the page cannot reach a session, a terminal or /ws. That set is a ceiling to be narrowed from audit evidence, never widened by one.
  • Twelve hours. A first value, expected to be wrong. What matters is that expiry exists and that the audit log can show whether it is being hit.
  • One record per login, named for the ceremony that produced it, so an audit record attributes one browser session rather than a role.
  • The browser holds it in memory only — in a closure, not localStorage, not a cookie. A reload runs the ceremony again. On a machine with no platform authenticator, that makes every reload a physical act, and that cost is chosen deliberately over persistence.
  • Signing out is revoking that one record. 
    $ relay credential revoke --id 69a9acee-a6a8-4be9-aa3a-a11c6135ef86
revoked credential "69a9acee-a6a8-4be9-aa3a-a11c6135ef86"
  name:    login 3FPKcJeU-R7J… 2026-08-28T23:12:59Z
  classes: read,configure
  its token stops authenticating on the next request; nothing else was touched

The bootstrap code, which is not a credential

relay login enrol prints a code. It authorises exactly one thing — registering a passkey — and is never accepted in place of an assertion, so it cannot become a password. It never authenticates a request to the API on its own.

$ relay login enrol
login code: 923f24dfdd66…
  expires:   2026-08-28T23:12:28Z (valid for 2m0s, single use)
  this code registers a passkey — it is NOT a password and is never accepted in place of one
  open http://localhost:8790/relay/login and enter it to register a passkey
  this code is shown ONCE and is not recoverable

Only its SHA-256 and expiry are stored, and there is at most one live at a time — running enrol twice replaces rather than accumulates. Run without RELAY_API_LISTEN set, the command cannot tell you where to redeem it, and says so instead of guessing:

$ relay login enrol
login code: ec4cffd80839…
  expires:   2026-08-28T23:12:28Z (valid for 2m0s, single use)
  this code registers a passkey — it is NOT a password and is never accepted in place of one
  open the relay login page (http://localhost:<RELAY_API_LISTEN port>/relay/login) and enter it to register a passkey
  this code is shown ONCE and is not recoverable

3. The class model, and the line under execute

A capability's class is a property of what it can cause, never of which tab it appears on. There are five.

ClassBlast radiusRoutes
read Discloses configuration or history. Changes nothing. GET /api/projects, GET /api/projects/{id}, GET /api/services, GET /api/services/{id}, GET /api/enrolments, GET /api/enrolments/{id}, GET /api/remote, GET /api/mcps, GET /api/mcps/{id}/tools, GET /api/mcps/{id}/scope_fields, GET /api/audit, GET /api/audit/log, POST /api/mcps/{id}/enumerate
configure Changes relay's own state, within decisions the operator already made. POST /api/projects, PUT /api/projects/{id}, DELETE /api/projects/{id}, POST /api/projects/{id}/regen_skill, DELETE /api/services/{id}, POST /api/services/{id}/start, POST /api/services/{id}/stop, PUT /api/services/{id}/autostart, DELETE /api/mcps/{id}, POST /api/audit/export
grant Issues or revokes a credential another party holds. POST /api/projects/{id}/rotate_token, POST /api/enrolments, DELETE /api/enrolments/{id}
execute The caller supplies what runs, or what is exposed. POST /api/mcps, POST /api/services, PUT /api/services/{id}, PUT /api/remote
proxy Reaches a surface relay has not classified. the / catch-all — every route an enhanced service registers via its manifest, /ws included

POST /api/mcps/{id}/enumerate is read despite being a POST: it asks a connected MCP for a scope field's real values and changes nothing. The method is not the classification; the blast radius is.

Why service create is execute and service start is not

The line under execute is not "a process starts". POST /api/services/{id}/start launches one and is merely configure. The line is who chose what runs.

Starting an already-configured service acts on a decision the operator already made. Writing the command field makes that decision — and a caller who can write a command and then start it has made relay execute an arbitrary program as the host user. That is the whole classification, and it is why POST /api/services and PUT /api/services/{id} sit in execute alongside POST /api/mcps, while start, stop and autostart do not. The same test puts PUT /api/remote in execute: it chooses the address the mTLS listener binds.

proxy is a class of its own rather than execute for a different reason: what the catch-all reaches is whatever a manifest declares, which relay cannot see and therefore cannot bound. Calling it execute would also hand the legacy frontend token POST /api/mcps and PUT /api/services/{id} — the two things the migration exists to withhold. Naming it as unclassified is the honest answer until the manifest protocol can describe per-route blast radius.

4. Transport is part of the grant

Relay's control plane has two doors, and they carry different route sets on purpose.

The 0600 Unix socket

Always present. Relay creates it in the config directory, one per process:

$ ls -l /tmp/relaydoc/relay-frontend-*.sock ; ls -ld /tmp/relaydoc
srw-------  1 admin  wheel  0 Aug 28 16:09 /tmp/relaydoc/relay-frontend-18066.sock
drwx------  6 admin  wheel  192 Aug 28 16:14 /tmp/relaydoc

Its authority is the filesystem: the kernel refuses a connection from any other user, and it does so before relay sees a byte. That is a real, checkable property of the listener, known at bind time — not an inference about a peer. (Relay refuses to use the caller's pid as an authorization input for exactly the opposite reason: a pid is reusable and racy.)

Dial it with curl --unix-socket:

$ curl -sS -i --unix-socket /tmp/relaydoc/relay-frontend-18066.sock \
       -H "Authorization: Bearer d015a0929972172b…" \
       -H 'Content-Type: application/json' -d '{"id":"demo","command":"/bin/echo hi"}' \
       http://localhost/api/services
HTTP/1.1 400 Bad Request
Content-Type: application/json

{"error":"display name is required"}

A 400 from the handler is the point: the execute route exists here, the credential holds execute, and the request reached validation.

The opt-in loopback TCP bind

Absent unless you ask. Set RELAY_API_LISTEN and relay binds a second listener beside the socket, and says so loudly:

level=WARN msg="frontend API bound to loopback TCP in addition to its socket" addr=127.0.0.1:8790

The address must be loopback. A non-loopback bind is refused outright rather than downgraded to the socket alone, because someone who asked for a TCP door and silently did not get one would debug the wrong thing:

$ RELAY_API_LISTEN=0.0.0.0:8792 relay
level=ERROR msg="failed to bind API listener" error="api listen address must be loopback: \"0.0.0.0:8792\""
$ echo $?
1

Classing narrows what a stolen credential reaches; it is not a transport authentication scheme. Reachability is still the only boundary against a network attacker, and a typo must not be the thing that removes it. This bind remains a development affordance, not a supported deployment.

Why execute and proxy are absent from TCP, not refused on it

Route registration goes through one function, RouteRegistrar.Handle, which takes the class and the transport the mux is being built for. When the class is not reachable on that transport, it registers nothing at all — not a wrapped handler that checks and refuses.

The difference is the whole of it. A policy check inside a handler is code someone can later invert, wrap or forget, and a 403 from inside a handler is still a route someone reached. A pattern that was never handed to that mux has no code path on that listener for a later change to get wrong. Relay applies the same reasoning to its remote dispatch table, which holds two entries so that a new admin operation is unreachable from a VM until somebody adds it to a list that is visibly a security boundary.

The consequence, stated so it is not discovered later: a browser-based view can never register an MCP, create a service, or reach a proxied route. Those stay on the socket. That is a real functional cost and the intended one.

What a caller actually observes there

Because the route was never registered, the refusal comes from Go's http.ServeMux, not from relay's authorization layer. Two shapes, and which one you get depends only on whether another method holds the same path.

405, when a sibling route holds the path. All four execute routes have a read or configure sibling that is routed on TCP, so in practice this is what you always see for execute. The Allow header tells you what survived:

$ curl -sS -i -H "Authorization: Bearer d015a0929972172b…" \
       -H 'Content-Type: application/json' -d '{}' \
       http://127.0.0.1:8790/api/services
HTTP/1.1 405 Method Not Allowed
Allow: GET, HEAD
Content-Type: text/plain; charset=utf-8

Method Not Allowed

$ curl -sS -i -X PUT -H "Authorization: Bearer d015a0929972172b…" \
       -H 'Content-Type: application/json' -d '{}' \
       http://127.0.0.1:8790/api/remote
HTTP/1.1 405 Method Not Allowed
Allow: GET, HEAD

404, when nothing holds the path. The proxy catch-all is the mount that would otherwise have absorbed every unmatched path. It is socket-only, so on TCP there is no catch-all and an unmatched path is simply not there:

$ curl -sS -i -H "Authorization: Bearer 0e4fd44e6e6bc693…" http://127.0.0.1:8790/v1/sessions
HTTP/1.1 404 Not Found
Content-Type: text/plain; charset=utf-8

404 page not found

Compare the same request on the socket, where the catch-all is mounted, with a credential that lacks proxy. Now the refusal comes from relay, and it is a 403:

$ curl -sS -i --unix-socket /tmp/relaydoc/relay-frontend-18066.sock \
       -H "Authorization: Bearer 0e4fd44e6e6bc693…" http://localhost/v1/sessions
HTTP/1.1 403 Forbidden
Content-Type: text/plain; charset=utf-8

Forbidden

Reading a status here. On TCP, 405 or 404 means no such route on this listener — it says nothing about your credential, and no amount of re-minting will change it. Move to the socket. 403 means the route exists and your credential lacks the class — re-mint naming it. 401 means the bearer resolved to no live credential at all.

5. The two gates

Two checks run on every request, in this order, and they answer different questions.

  1. frontendCredentialAuth — "is this anyone?" It resolves the request's Authorization: Bearer against every record in api_credentials, comparing SHA-256 in constant time, before any handler runs. An unauthenticated WebSocket upgrade therefore never allocates a session.
  2. RouteRegistrar — "may they do this?" Each route was registered under a class; the wrapper resolves the bearer to a credential again, attaches its id to the request context, and then checks the class.

Only the second may narrow. The two were briefly conflated once, with the outer check admitting exactly one fixed token — which made every other credential unreachable and the class model dead code. That defect is the reason the layering is written down.

Fail closed, and say nothing

Absent, malformed and unknown bearers all get the same 401 with the same body. So does an expired credential. That uniformity is deliberate: a distinguishable answer would be an oracle for which credentials exist, and "this credential existed once" is a fact a bearer relay refuses should not be able to establish.

$ curl -sS -i http://127.0.0.1:8790/api/projects | head -6
HTTP/1.1 401 Unauthorized
Content-Type: text/plain; charset=utf-8
X-Content-Type-Options: nosniff
Content-Length: 13

unauthorized

$ curl -sS -i -H "Authorization: Bearer not-a-token" http://127.0.0.1:8790/api/projects | head -6
HTTP/1.1 401 Unauthorized
Content-Type: text/plain; charset=utf-8
X-Content-Type-Options: nosniff
Content-Length: 13

unauthorized

An empty credential set also fails closed. A settings file that is missing, corrupt, truncated or unreadable resolves to empty settings for a reader, and empty means every request is refused — serving open would silently expose every proxied service. This is why deleting settings.json works as a way to lock the control plane out.

Why the login routes are a separate mux

The three login patterns are served with no credential at all. They live in their own http.ServeMux that is consulted before frontendCredentialAuth — not as an exemption inside the authenticated mux.

An exemption is a second gate in front of the mux that already authenticates, and a second gate shadowing the first is precisely the defect that had to be fixed once already. A separate mux also means a fourth unauthenticated pattern has to be added to a short list somebody reviews, rather than discovered to already work.

The public surface is exactly three (method, path) pairs. A request to the right path with the wrong method does not match, and falls through to the authenticated side:

$ curl -o /dev/null -w '%{http_code}\n' -X POST http://localhost:8790/relay/login          # public route, wrong method
401
$ curl -o /dev/null -w '%{http_code}\n' http://localhost:8790/relay/login/challenge        # POST-only, asked with GET
401
$ curl -o /dev/null -w '%{http_code}\n' http://localhost:8790/relay/login/status           # no such pattern
401

/relay/ is reserved: a service manifest that tries to claim a route under it is refused at registration, so nothing can shadow the login page. And the login routes exist only where a TCP listener is bound, because a WebAuthn ceremony is verified against an origin and a Unix socket has none. Over the socket, /relay/login is just another path under the catch-all:

$ curl -o /dev/null -w '%{http_code}\n' --unix-socket /tmp/relaydoc/relay-frontend-18066.sock \
       http://localhost/relay/login
401
$ curl -o /dev/null -w '%{http_code}\n' --unix-socket /tmp/relaydoc/relay-frontend-18066.sock \
       -H "Authorization: Bearer 0e4fd44e6e6bc693…" http://localhost/relay/login
403

6. The passkey ceremony, step by step

Relay authenticates its owner with WebAuthn: ES256, user verification required. There is no password and no set-a-password flow. The argument is not that passkeys are modern — it is that a password verifier is a new kind of secret in settings.json. Every other value there is either a hash of something relay issued or a token whose compromise relay bounds. A password is offline-guessable, chosen by a human, and reused, so its compromise reaches systems relay has never heard of. It is also phishable, and the only new attack surface this whole feature opens is "a page in the owner's browser".

The cost is real and worth stating: the relying-party id is pinned to localhost because an RP ID must be a registrable domain, so http://127.0.0.1:PORT cannot carry the ceremony at all. The bind address stays what it is; the URL you type is part of the design.

Registration is not self-service

Registering a passkey is the point at which a new identity is created, and relay refuses to let that be reachable by presenting a secret over the network. The anchor is a code minted by a CLI running as the user who owns the config directory.

Trust-on-first-use was considered and refused. The window is not a harmless few seconds: any page the owner visits can POST to a loopback bind, so the race is not between the owner and an attacker who has to get there first — it is between the owner and every open tab. And the window would reopen, because deleting settings.json is a documented way to lock the control plane out, and under TOFU that act would silently re-arm self-registration. A boundary that a documented recovery procedure disarms is not a boundary.

What the anchor does not defend against is the user who owns the config directory: that user can read every project token in settings.json and write a bootstrap record of their own. Relay has never defended the config dir against its owner and does not start here. What it defends is the new surface — a page in the browser, or anything reaching the loopback port through a tunnel, cannot read the config dir and cannot produce the code.

The ceremony

The same ceremony, with the real bytes

The transcript below is a real Chrome, driven headless against a relay bound at 127.0.0.1:8790, recorded from inside the page by wrapping fetch. Long base64 fields are cut; nothing else is edited.

Challenge, registration

POST /relay/login/challenge  →  200
request : {"ceremony":"register"}
response: {"challenge":"YoJFJuILhmYHJ4m4KrxaMBVp9MZKZRzxC-5HV_3cWXg",
           "rp_id":"localhost","origin":"http://localhost:8790",
           "user_handle":"cmVsYXktb3duZXI","user_name":"relay owner","credentials":[]}

The challenge is 32 random bytes, single use, valid 60 seconds, in a fixed table of 64 entries. user_handle decodes to the constant relay-owner: an authenticator stores the handle it was given at registration and returns it on every assertion, so it must be byte-identical across two ceremonies that share no state, and relay has exactly one owner.

navigator.credentials.create, and what Chrome produced

POST /relay/login/verify  →  201

           "client_data_json":"eyJ0eXBlIjoid2ViYXV0aG4uY3JlYXRlIiwiY2hhbGxlbmdl…",

           "name":"browser passkey 2026-08-28T23:12:56Z"}

Decoded, that clientDataJSON is (from the live-Chrome test, which prints it):

{"type":"webauthn.create",
 "challenge":"XLS8fi4-l0Z8c2Fk0AGDfNoeSu49bX7PatAcbR7XJ6E",
 "origin":"http://localhost:56486",
 "crossOrigin":false}

chrome attestation: fmt="none" aaguid=01020304050607080102030405060708 flags=0x45 signCount=1 authData=164 bytes

What relay verifies, in order. The challenge is consumed — lookup and delete under one lock, so an unknown challenge, an expired one, one already spent and one issued for the other ceremony are one answer and a replay races nothing. Then type is webauthn.create; origin equals the origin derived from the address the kernel actually gave the listener, never a header or a setting; crossOrigin is not true. Then the attestation object must be exactly the three-key none shape with an empty statement — any other format, a non-empty statement or a fourth key is a refusal. Then the authenticator data: the RP ID hash matches SHA-256("localhost"), the user-present and user-verified flags are both set, extension data is refused outright, and there must be no trailing bytes beyond what the flags imply. Then the COSE key must be exactly five entries describing an ES256 key on P-256, and the point must be on the curve.

Only then does relay touch settings, and it does the cap check, the duplicate check and the bootstrap-code check inside the same write:

  • The cap (five passkeys) and the duplicate check are re-run at commit even though the verifier already ran them, because the verifier ran them against a snapshot read before the ceremony and two registrations racing would both pass it.
  • The code is consumed only once the record is certain to land, so a refused registration does not spend the operator's anchor.
  • A refusal declines the write. Nothing is saved and the file is left byte for byte as it was — otherwise every refused registration, which needs no code and no credential, would be a trigger on relay's settings writer for anything that can reach the listener.

Assertion

POST /relay/login/challenge  →  200

response: {"challenge":"oUShAqIXrI4pSfbgHUtwpsWvvCCJMOCM_9KkUKr96tA",
           "rp_id":"localhost","origin":"http://localhost:8790",
           "credentials":["3FPKcJeU-R7JowWNdy4yZ5ludF8QtA30RALSPhUsbfc"]}

That credentials array is a stated cost. Refusing discoverable credentials means allowCredentials has to be supplied, so this endpoint hands an unauthenticated caller the registered credential ids. They are opaque, they are not verifiers, and the login document discloses that passkeys exist anyway.

POST /relay/login/verify  →  200
request : {"ceremony":"assert",
           "credential_id":"3FPKcJeU-R7JowWNdy4yZ5ludF8QtA30RALSPhUsbfc",
           "client_data_json":"eyJ0eXBlIjoid2ViYXV0aG4uZ2V0IiwiY2hhbGxlbmdlIjoib1VTaEFxSVhy…",
           "authenticator_data":"SZYN5YgOjGh0NBcPZHZgW4_krrmihjLHmVzzuoMdl2MFAAAAAg",
           "signature":"MEQCIETSipIoEU7Q6uYnWFUgSdUxcc-Tj5lmatlGQhg2MiqKAiBc7Uw_va3ttRgMNux-sSowgNwmFBcvYMgipGEQ2-0EBQ",
           "user_handle":""}
response: {"token":"752aca69b7324bac…","expires":"2026-08-29T11:12:59Z","classes":["read","configure"]}

The assertion's clientDataJSON, decoded, ends with a member relay does not know about:

{"type":"webauthn.get","challenge":"oUShAqIXrI4pSfbgHUtwpsWvvCCJMOCM_9KkUKr96tA",
 "origin":"http://localhost:8790","crossOrigin":false,
 "other_keys_can_be_added_here":"do not compare clientDataJSON against a template. See https://goo.gl/yabPex"}

That member is why relay parses client data permissively about unknown JSON fields while being strict about everything else: the specification reserves the right to add them and browsers already ship one. Rejecting unknown members here would be a refusal of real user agents, not of attacker input. (The request bodies to /relay/login/*, by contrast, are decoded with unknown fields disallowed.)

What relay verifies on an assertion. Challenge, type, origin and cross-origin as before; the credential id must resolve to a stored passkey; if a user handle is sent it must match the stored one; the authenticator data must be exactly 37 bytes with no attested credential data; RP ID hash, user present, user verified. Then ECDSA over SHA-256(authenticatorData ‖ SHA-256(clientDataJSON)) against the stored public key. A credential id that resolves to nothing and a signature that does not verify get the same answer — splitting them would tell an unauthenticated caller which credential ids exist.

Finally the signature counter must strictly increase, which is the cloned-authenticator signal. If an authenticator reported counter 0 at registration, relay fixes that credential as counter-less for good, so a later 0 is not misread as a clone. A counter failure is audited with its detail and answered to the caller in the words of an ordinary rejected assertion.

The login page itself

The page loads nothing — no CDN, no framework, no external font, no image — and says so in a header rather than by habit:

$ curl -sS -D - -o /dev/null http://localhost:8790/relay/login
HTTP/1.1 200 OK
Cache-Control: no-store
Content-Security-Policy: default-src 'none'; script-src 'nonce-B2LoOoedv4Us2+EHzwfhSw'; style-src 'nonce-B2LoOoedv4Us2+EHzwfhSw'; connect-src 'self'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'
Content-Type: text/html; charset=utf-8
Referrer-Policy: no-referrer
X-Content-Type-Options: nosniff

The nonce is fresh on every render. connect-src 'self' is the one thing the policy must allow: the page's own fetches back to the two POST routes. The document is small and hand-written on purpose — every parameter that matters (ES256 only, user verification required, resident key discouraged, allowCredentials on every assertion) is visible in one screen of JavaScript rather than assembled by a library.

The POST routes require Content-Type: application/json, which is not decoration. A content type outside the three an HTML form can produce forces the browser to preflight a cross-origin POST, and relay answers no preflight and emits no CORS header — so a page on another origin cannot reach these routes at all, on top of the origin binding the ceremony itself carries.

$ curl -sS -i -X POST -H 'Content-Type: application/x-www-form-urlencoded' \
       -d 'ceremony=register' http://localhost:8790/relay/login/challenge
HTTP/1.1 400 Bad Request
Content-Type: application/json

{"error":"login: malformed request: content type \"application/x-www-form-urlencoded\""}

$ curl -sS -X POST -H 'Content-Type: application/json' \
       -d '{"ceremony":"assert","password":"hunter2"}' http://localhost:8790/relay/login/verify
{"error":"login: malformed request: json: unknown field \"password\""}

Losing the authenticator, and revoking one

There is deliberately no second factor, no backup code and no recovery question — each of those is a phishable shared secret wearing a different hat. The recovery path is the host: relay login enrol registers another passkey, and relay credential mint bypasses the browser entirely. Anyone who can run those already owns the config directory.

Revoking a passkey stops the next login and does not end sessions it already signed in. Those are two records with two lifetimes, and the CLI says so at the point of the act:

$ relay login revoke --id 3FPKcJeU-R7JowWNdy4yZ5ludF8QtA30RALSPhUsbfc
revoked passkey "browser passkey 2026-08-28T23:12:56Z"
  id: 3FPKcJeU-R7J…
  it can no longer complete a login assertion; nothing else was touched
  browser sessions this passkey already signed in are NOT ended — see `relay credential list`, or Settings → Passkeys

revoke --id takes the full credential id, not the abbreviated form the listing prints — an abbreviation is ambiguous:

$ relay login revoke --id "3FPKcJeU-R7J…"
error: no passkey found with id "3FPKcJeU-R7J…"

7. What gets audited, and what does not

relay audit is ground truth for anything relay gates. Every authorization decision on the control plane — allowed or refused — is a control_decision record with the same standing as a tool-call denial.

One record, raw:

$ relay audit --kind control --tail 1 --json
{"id":"c7144fb1-c68f-4c7a-ad70-ed0a5a16af36","ts":"2026-08-28T23:10:14.714091Z","dur_ms":0,
 "event":"control_decision","actor":{"kind":"control","auth":"token","cred_id":"0c49e4b1-c5fb-420b-a473-6685b9403769"},
 "outcome":"denied","error":"class not granted","scope":null,
 "method":"GET","path":"/v1/sessions","class":"proxy","transport":"socket"}

What is in a record

  • Method, path, class, transport and credential id. The decision is recorded before the handler runs, so a panic or a slow handler cannot suppress it — it is a record of the authorization decision, not of the handler's outcome.
  • The credential id is attached as soon as the bearer resolves, before the class check, so a class refusal still names the credential that attempted it. Only an unresolved bearer leaves it blank, since there is no credential to name.
  • Method and path are capped (32 and 1024 bytes), because they are read off the request line before any credential has been resolved: a caller holding no class at all still reaches this record on every refusal.
  • Login ceremonies carry an empty class. Those routes are not registered through RouteRegistrar and there is no class that means "none"; inventing one would put the hole in the vocabulary into a record.
  • For a login, cred_id is the credential that was minted, which is what makes a browser session attributable. For a registration it is the abbreviated passkey id.

What is deliberately not in one

  • The 401s. A bearer that resolves to nothing is refused by frontendCredentialAuth, which is in front of the registrar, so no control_decision is written. In the transcript above, several unauthenticated requests were made and none appear. They are logged at WARN level, not audited.
  • The 404s and 405s on TCP. No handler ran and no authorization decision was taken, so there is nothing to record. A route that is not on a listener produces silence in the audit log — which is another reason to read the status rather than the log when debugging transport.
  • Any secret. No token, no stored hash, no bootstrap code, from any field. A refusal records the sentinel relay itself wrote rather than the error's full text, because a decode failure quotes the body it choked on and the body of a registration is where a caller's guess at the anchor lives. The counter refusal is the one exception, and its detail is relay's own — a stored credential id and two stored counters.
  • Refusals from before a ceremony was attempted — a malformed body, an unknown ceremony name. They are reachable at line rate by anything that can open a socket and say nothing about a login.
  • Refusals the ceremony limiter itself produced. This one is visible in a transcript. Six identical bad assertions in a row: 
    attempt 1: 403 retry-after= {"error":"webauthn: unknown, expired or already used challenge"}
attempt 2: 403 retry-after= {"error":"webauthn: unknown, expired or already used challenge"}
attempt 3: 429 retry-after=2 {"error":"too many failed login ceremonies: retry after 2s"}
attempt 4: 429 retry-after=2 {"error":"too many failed login ceremonies: retry after 2s"}
attempt 5: 429 retry-after=2 {"error":"too many failed login ceremonies: retry after 2s"}
attempt 6: 429 retry-after=2 {"error":"too many failed login ceremonies: retry after 2s"}
    produce two records, not six: 
    $ relay audit --kind control --tail 2
16:13:50  denied  -  -  -  0  -  POST /relay/login/verify  class=  transport=tcp  webauthn: unknown, expired or already used challenge
16:13:50  denied  -  -  -  0  -  POST /relay/login/verify  class=  transport=tcp  webauthn: unknown, expired or already used challenge
    The throttle is the one refusal an unauthenticated caller can provoke as fast as it can send. Recording it would be exactly the audit-log amplification the control-plane caps exist to prevent. The failures that caused the throttle are each recorded.

The limiter allows three failures, then delays by two seconds per failure over that, capping at thirty, and clears on a ceremony that completed end to end — including the parts the verifier cannot see. It returns the delay rather than sleeping: a verifier that slept would hold a goroutine per attempt, which is a cheaper denial of service than the one being rate-limited.

A challenge flood is a denial of service relay bounds but cannot prevent. POST /relay/login/challenge allocates an entry in a fixed table (64 entries, 60 seconds, single use) and is unauthenticated by construction; on a loopback bind every request arrives from the same address, so there is no identity to reserve a slot against. A flood that keeps issuing as entries expire keeps the owner refused for as long as it runs. What is bounded is what it costs relay — a fixed table, no disk, no goroutine — and the condition is not silent: a full table logs a warning at most once per TTL, which is the difference between an operator seeing "login is broken" and seeing that something is hammering the login route. The CLI is the recovery path, as it is for every other login failure.

8. Failure modes you will actually hit

401 on a request that worked yesterday

What you see. HTTP/1.1 401 Unauthorized with the body unauthorized. Nothing in relay audit --kind control.

What it means. The bearer resolved to no live credential. Four causes are indistinguishable on purpose: no header, a malformed one, an unknown token, and an expired credential.

What to do. relay credential list --include-expired. If your credential is there marked (expired), that is your answer. If it is a browser login, run the ceremony again — a reload does that by itself. If the whole list is empty, relay is failing closed on an unreadable or missing settings.json; check relay.log for no API credentials configured. If your token is a RELAY_FRONTEND_TOKEN captured from an earlier process, it is stale — relay mints a new one each start.

"invalid or expired login code"

What you see. In the page: Registration refused: invalid or expired login code. On the wire, 403 with {"error":"invalid or expired login code"}. In the audit log, a denied record on POST /relay/login/verify with that reason and no credential id.

What it means. One of: the code was already spent, it is older than two minutes, a later relay login enrol replaced it, or it was never right. Those are refused identically, so that a caller who cannot read the config directory cannot learn whether registration is currently anchored at all.

What to do. Run relay login enrol again and redeem it promptly. Two minutes is the whole design: the window between minting and redeeming should be a deliberate, momentary act, not something you forget was open. Note that a refused registration leaves settings.json untouched — no half-registered passkey to clean up — and does not spend a later code.

403 Forbidden

What you see. HTTP/1.1 403 Forbidden, body Forbidden, and a denied … class not granted record naming your credential id and the class the route wanted.

What it means. You authenticated. The route exists on this transport. Your credential does not hold its class.

What to do. Read the class off the audit record — it is the authoritative answer, not this page's route table — and mint a credential naming it. Remember that classes do not nest: relay credential mint --name my-rotator --class grant --class read if you need both. If the credential in question is legacy-frontend-token, you cannot widen it; mint your own.

405 or 404 on the loopback bind

What you see. 405 Method Not Allowed with an Allow header, or 404 page not found. Nothing in the audit log at all.

What it means. The route is not registered on this listener. Your credential is irrelevant — an execute-class credential gets the identical refusal. This is execute (service create/update, MCP register, remote bind) or proxy (anything an enhanced service registers, /ws included).

What to do. Use the socket: curl --unix-socket "$RELAY_FRONTEND_SOCKET" http://localhost/api/…. There is no flag, setting or credential that puts these routes on TCP; the registration never happens. If you are writing a browser-side view, treat this as a design constraint rather than a bug — those actions stay on the host.

Connection refused, or no /relay/login at all

What you see.

$ curl -sS http://localhost:8791/relay/login
curl: (7) Failed to connect to localhost port 8791 after 0 ms: Couldn't connect to server

and, in relay's log, a frontend server bound line with a socket and no frontend API bound to loopback TCP line after it.

What it means. RELAY_API_LISTEN was not set for that process. There is no socket at all — not a closed one, not one that refuses. An install that never asked for a browser door has no browser-facing network surface, and the login routes are registered nowhere rather than registered against a placeholder origin.

What to do. Restart relay with RELAY_API_LISTEN=127.0.0.1:PORT. Confirm with lsof -nP -iTCP:PORT -sTCP:LISTEN, and check that relay login enrol now prints a URL rather than the <RELAY_API_LISTEN port> placeholder. If relay exited at startup instead, look for failed to bind API listener — a non-loopback address is refused outright.

A revoked passkey that did not sign anyone out

What you see. relay login revoke succeeded, and a browser tab keeps working.

What it means. The passkey and the credentials it minted are separate records with separate lifetimes. Revoking the passkey stops the next assertion; it does not touch a credential already issued, which lives up to twelve hours.

What to do. relay credential list, find the record whose name starts with login , and relay credential revoke --id …. Or Settings → Passkeys → Signed-in Browsers → Sign out, which does the same thing and refuses anything that is not a login credential.
